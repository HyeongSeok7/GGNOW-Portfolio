# GGNOW

> **경기도 행사 · 축제 정보를 한눈에 조회하고 서비스를 제공할 수 있는 웹 서비스**  
> 공공데이터 API를 활용해 행사 정보를 제공하고, 회원 기능을 통해 **즐겨찾기**, **리뷰**, **마이페이지**까지 사용할 수 있도록 구현한 백엔드 중심 포트폴리오 프로젝트입니다.

---

## 프로젝트 개요

GGNOW는 경기도 행사·축제 정보를 카테고리별로 조회하고, 사용자가 관심 행사를 즐겨찾기, 후기 등 기능을 이용할 수 있는 웹 서비스입니다.

이 프로젝트는 단순 CRUD 구현에 더해 **외부 API 데이터 정제, 내부 식별자 설계, 인증/인가, 사용자 데이터 연결, 배포 환경 문제 해결**에 중점을 두고 개발했습니다.

### 이 프로젝트에서 중점적으로 구현한 부분

- 외부 API의 전체 페이지를 수집한 뒤 DB에 반영하는 동기화 구조 구현
- 사용자 요청은 외부 API가 아닌 내부 DB를 조회하도록 수집·조회 경로 분리
- API 호출 실패 및 비정상 응답 시 기존 저장 데이터를 활용하도록 처리
- 원본 상세 문서 ID 기반 행사 식별과 SHA-256 고정 길이 키 적용
- 기존 행사 ID를 유지하는 갱신 처리로 리뷰·즐겨찾기 연결 보존
- Spring Security 기반 인증, CSRF 보호 및 BCrypt 비밀번호 해싱 적용
- 리뷰 작성자 권한과 종료·비활성 행사에 대한 변경 요청 검증
- 카테고리·종료 행사 목록에 16개/32개 서버 DB 페이징 적용
- 행사 카드 이미지에 지연 로딩 적용
- JUnit 5와 Mockito 기반 단위 테스트 작성
- Docker, Render, Aiven DB를 활용한 배포 경험

## 주요 기능

### 1. 행사 목록 조회 및 서버 DB 페이징
- Spring Scheduler가 외부 API에서 행사 데이터를 수집해 내부 DB에 저장합니다.
- 서비스 화면은 외부 API를 직접 호출하지 않고, DB에 저장된 행사 데이터만 조회합니다.
- 따라서 외부 API 호출이 실패해도 마지막 정상 동기화 데이터를 기반으로 목록·검색·상세 기능을 제공합니다.
- 공연 / 교육 / 문화 / 전시 카테고리를 분리해 조회할 수 있습니다.
- 카테고리 목록은 Spring Data JPA `Page` 기반 서버 DB 페이징으로 처리했습니다.
- 페이지당 표시 수는 16개 또는 32개를 지원합니다.
- 최신순(`beginDe DESC`)과 마감임박순(`endDe ASC`) 정렬을 지원합니다.

### 2. 행사 검색
- 사용자가 입력한 키워드를 기준으로 행사 정보를 검색할 수 있습니다.
- 검색 시 단순 제목 비교가 아니라, 공백과 특수문자를 정리한 정규화 값을 기준으로 비교합니다.
- 행사 제목뿐 아니라 **주최 기관명, 주소**도 함께 검색 대상에 포함하여 사용자가 더 쉽게 행사를 찾을 수 있도록 개선했습니다.

### 3. 행사 상세 조회
- 목록, 검색 결과, 마이페이지에서 내부 DB 식별자인 `festivalId`로 상세 페이지에 접근합니다.
- 신규·갱신 행사의 `identityKey`는 GGC 원본 상세 URL의 문서 ID를 기준으로 생성합니다.
- 제목, 일정, 참가비가 수정되어도 원본 문서 ID가 같으면 기존 DB 행사를 갱신합니다.
- 종료 행사에 일반 상세 주소로 접근하면 종료 행사 상세 페이지로 이동합니다.

### 4. 회원가입 / 로그인
- 회원가입 시 **아이디 5~20자 길이 검증**과 **아이디 중복 확인** 기능을 제공합니다.
- Spring Security 기반 로그인 / 로그아웃을 구현했습니다.
- 비밀번호는 **6~12자, 영문과 숫자 각각 1개 이상 포함** 규칙을 적용했습니다.
- 비밀번호는 **BCrypt**로 암호화하여 저장합니다.

### 5. 즐겨찾기
- 로그인한 사용자는 진행 중인 관심 행사를 즐겨찾기에 추가할 수 있습니다.
- 서버에서 행사 ID 형식, 실제 행사 존재 여부, 종료·비활성 상태를 검증합니다.
- 중복 추가 요청을 처리하며, 마이페이지에서 즐겨찾기 목록을 확인할 수 있습니다.
- 즐겨찾기 삭제는 로그인한 사용자 본인의 항목을 대상으로 수행합니다.

### 6. 리뷰 기능
- 로그인한 사용자는 진행 중인 행사에 리뷰를 작성할 수 있습니다.
- 리뷰 수정·삭제 시 행사 일치 여부와 작성자 본인 여부를 서비스 계층에서 검증합니다.
- 종료되었거나 비활성화된 행사에는 리뷰 작성·수정·삭제를 허용하지 않습니다.
- 종료 행사 상세에서는 기존 리뷰를 읽기 전용으로 제공합니다.
- 마이페이지에서 본인이 작성한 리뷰를 조회할 수 있습니다.

### 7. 비밀번호 변경
- 현재 비밀번호 검증 후 새 비밀번호로 변경할 수 있습니다.
- 비밀번호 변경 후에는 보안을 위해 다시 로그인하도록 처리했습니다.

### 8. 행사 데이터 자동 동기화 및 상태 관리
- 서버 시작 10초 후 최초 동기화를 실행하고, 이후 한국 시간 기준 매일 자정에 실행합니다.
- API의 0페이지부터 정상적인 빈 페이지 또는 데이터 없음 응답까지 순차 수집합니다.
- 반환 개수가 요청 개수보다 적더라도 마지막 페이지로 단정하지 않습니다.
- 응답 코드·형식, 원본 URL, 날짜 형식을 검증하며 반복 페이지와 최대 페이지 수 초과를 감지합니다.
- 전체 수집이 성공한 경우에만 DB 저장 트랜잭션을 실행합니다.
- 기존 데이터는 저장된 원본 URL로 매칭하여 내부 `festivalId`를 유지하면서 갱신합니다.
- 수집 결과에 없는 행사는 물리 삭제하지 않고 `active=false`로 변경합니다.
- API 수집 실패 또는 전체 빈 응답 시 API 결과의 DB 반영을 건너뜁니다.
- 종료일 경과에 따른 비활성화는 API 수집과 별도로 수행합니다.
- DB 반영까지 성공한 경우에만 `SyncStatus`의 마지막 성공 시각을 갱신합니다.
- 같은 서버 프로세스 내에서 동기화 작업이 중복 실행되지 않도록 제어합니다.

### 9. 종료 행사 보관함

- 종료일이 (한국시간기준) 오늘보다 이전인 행사는 진행 중 목록에서 제외하고 종료 행사 보관함에서 별도로 조회합니다.
- 종료 행사도 문화 / 교육 / 전시 / 공연 카테고리로 필터링할 수 있습니다.
- 종료 행사 보관함에도 16개 / 32개 보기와 서버 DB 페이징을 적용했습니다.
- 종료 행사 상세 페이지에서는 행사 정보와 기존 리뷰를 조회할 수 있습니다.

## 주요 엔드포인트

### 페이지 라우팅
- `GET /main` : 메인 페이지
- `GET /culture` : 문화 행사 카테고리 페이지
- `GET /education` : 교육 행사 카테고리 페이지
- `GET /exhibition` : 전시 행사 카테고리 페이지
- `GET /performance` : 공연 행사 카테고리 페이지
- `GET /festival/id/{festivalId}` : 내부 식별자 기준 행사 상세 페이지
- `GET /festival/{title}` : 기존 제목 기반 접근 **호환용** 경로 (내부적으로 id 기반 상세 페이지로 연결)
- `GET /search?keyword={keyword}` : 행사 검색결과 페이지
- `GET /login` : 로그인 페이지
- `GET /register` : 회원가입 페이지
- `GET /mypage` : 마이페이지
- `GET /my-reviews` : 본인이 작성한 리뷰 조회 페이지
- `GET /change-password` : 비밀번호 변경 페이지
- `GET /customer` : 고객센터 페이지
- `GET /ended` : 종료 행사 보관함 및 카테고리 필터·DB 페이징
- `GET /ended/festival/{festivalId}` : 종료 행사 상세 및 기존 리뷰 조회

### 인증 / 회원
- `POST /register` : 회원가입 처리
- `GET /register/check-username?username={username}` : 아이디 길이 검증 및 중복 확인
- `GET /check-login` : 로그인 상태 확인

### 리뷰 API
- `GET /festivals/{festivalId}/reviews` : 특정 행사 리뷰 목록 조회
- `POST /festivals/{festivalId}/reviews` : 특정 행사 리뷰 작성
- `PATCH /festivals/{festivalId}/reviews/{reviewId}` : 특정 리뷰 수정
- `DELETE /festivals/{festivalId}/reviews/{reviewId}` : 특정 리뷰 삭제

### 즐겨찾기 API
- `POST /addFavoriteEvent` : 즐겨찾기 추가
- `GET /getFavoriteEvents` : 내 즐겨찾기 목록 조회
- `DELETE /removeFavoriteEvent` : 즐겨찾기 삭제

## 테스트

JUnit 5와 Mockito를 사용해 DB 연결 없이 서비스의 주요 로직을 검증했습니다.

### 검증 범위

- 회원가입과 아이디 중복 검증
- 리뷰 작성·수정·삭제와 작성자 권한 검증
- 종료 행사에 대한 신규 리뷰 작성 차단
- 즐겨찾기 등록·중복 확인·삭제
- 검색어 문자열 정규화
- 동일 원본 문서의 내용 변경 시 식별 키 유지
- 서로 다른 원본 문서의 식별 키 분리
- 잘못된 원본 URL 차단
- 요청 크기보다 짧은 페이지 이후에도 수집 지속
- 중간 API 실패 시 부분 결과 반환 차단
- 반복 페이지, 전체 빈 응답, 응답 코드 누락 처리
- 기존 행사 ID를 유지하는 갱신 처리
- 기존 원본 URL 누락·중복 시 저장 중단
- API 수집 실패 시 DB 반영 호출 차단

### 실행 방법

프로젝트 루트에서 실행합니다.

```powershell
.\gradlew.bat test --tests "com.project.web.service.*"
```

### 테스트 결과와 범위

서비스 단위 테스트 25개가 통과하는 것을 확인했습니다.

Repository와 외부 API 호출은 Mockito로 대체했습니다.
따라서 이 결과가 실제 MariaDB에서의 트랜잭션 롤백이나 전체 배포 환경의 정상 동작까지 보장하는 것은 아닙니다.
DB 연결이 필요한 `contextLoads()`는 별도 검증 대상입니다.

## ERD

![ERD](docs/images/ERD.png)

### 주요 엔티티
- **User** : 회원 정보 관리
- **Review** : 행사별 리뷰 저장
- **FavoriteEvent** : 회원별 즐겨찾기 행사 저장
- 현재 구현에서는 `event_id` 컬럼에 내부 행사 식별자인 `festival.id` 값을 문자열 형태로 저장합니다.
- 따라서 ERD에서는 `favorite_event.event_id`와 `festival.id`를 실제 FK가 아닌 논리적 참조 관계로 설명합니다.
- **FestivalEntity** : 외부 행사 정보를 저장하는 엔티티
  - `id` : 상세 페이지, 리뷰, 즐겨찾기에서 참조하는 내부 행사 식별자
  - `identityKey` : 신규·갱신 행사에 사용하는 원본 문서 ID 기반 SHA-256 키
  - `normalizedTitle` : 검색과 제목 비교를 위한 정규화 값
  - `title` : 화면 표시용 행사 제목
  - `homepage` : GGC 원본 상세 URL
  - `hmpgUrl` : 기관 또는 행사 공식 홈페이지 URL
  - `active` : 일반 행사 목록의 노출 여부
- **SyncStatus** : 마지막 DB 동기화 성공 시각 관리

## 설계 및 구현 포인트

### 1. 사용자 인증 및 보안
- Spring Security를 적용해 **비회원 접근 가능 페이지**와 **로그인이 필요한 기능**을 분리했습니다.
- 사용자 비밀번호는 `BCryptPasswordEncoder`를 사용해 암호화했습니다.
- 비밀번호 변경 시 현재 비밀번호를 검증하고, 변경 후에는 세션을 종료해 다시 로그인하도록 처리했습니다.

### 2. 외부 API 데이터 처리
- GGC Open API의 JSON 응답을 페이지 단위로 수집합니다.
- 정상적인 종료 응답을 확인한 경우에만 수집 결과를 DB 저장 단계에 전달합니다.
- API 서버가 반환 개수를 제한할 수 있으므로 짧은 페이지를 마지막 페이지로 단정하지 않습니다.
- 같은 원본 문서 ID의 중복 데이터에는 기존 데이터 선택 규칙을 적용합니다.
- 서로 다른 원본 문서는 제목이나 일정이 같더라도 자동으로 하나의 행사로 병합하지 않습니다.

### 3. 외부 원본과 내부 식별자 분리
- 원본 상세 URL에서 문서 ID를 추출하고 공급원 구분 문자열과 함께 SHA-256으로 변환합니다.
- 제목, 일정, 주소, 참가비 등의 변경 가능한 값은 행사 식별 키에서 제외합니다.
- 기존 DB 행사는 저장된 원본 URL로 찾아 내부 `festivalId`를 유지하면서 갱신합니다.
- 원본 URL이 없거나 동일 원본에 여러 DB 행사가 연결된 경우에는 임의로 병합하지 않고 동기화를 중단합니다.

### 4. API 수집과 DB 저장·조회 분리
- `FestivalSyncScheduler`는 실행 시점과 전체 작업 흐름을 관리합니다.
- `FestivalService`는 API 전체 페이지 수집과 DB 조회 기능을 제공합니다.
- `FestivalSyncWriter`는 수집 완료 결과의 DB 반영을 담당합니다.
- 외부 API 호출은 DB 저장 트랜잭션 밖에서 수행합니다.
- 사용자 요청에 따른 목록·검색·상세 조회는 내부 DB를 사용합니다.

### 5. 동기화 실패와 데이터 보존
- 중간 페이지 호출 실패, 비정상 응답, 반복 페이지 발생 시 부분 결과를 반영하지 않습니다.
- 전체가 빈 응답인 경우에도 기존 데이터를 일괄 비활성화하지 않습니다.
- DB 반영 과정에서 예외가 발생하면 해당 저장 트랜잭션이 롤백되도록 구성했습니다.
- 정상 수집 결과에 없는 행사는 물리 삭제 대신 비활성화합니다.
- 종료일 경과 처리는 API 수집 성공 여부와 별개로 수행합니다.
- 마지막 성공 시각은 DB 반영이 완료된 경우에만 갱신합니다.

### 6. 권한과 운영 설정
- Spring Security와 CSRF 보호를 적용합니다.
- 리뷰 수정·삭제는 작성자 본인인지 서비스 계층에서 확인합니다.
- 종료·비활성 행사에 대한 리뷰 변경 및 즐겨찾기 추가 요청을 서버에서 차단합니다.
- 즐겨찾기 추가 시 행사 ID 형식과 실제 행사 존재 여부를 검증합니다.
- 운영 설정에서는 SQL과 바인딩 값의 상세 로그를 출력하지 않도록 조정했습니다.

## 트러블슈팅 

### 1. 행사 중복 판단 기준 개선

#### 문제
- 초기에는 제목과 날짜·시간·주소·참가비를 조합한 fingerprint로 중복 여부를 판단했습니다.
- 이 방식은 내용이 같은 별도 원본 문서를 하나로 합치거나, 내용이 수정된 같은 문서를 다른 행사로 판단할 수 있었습니다.

#### 해결
- 중복 판단 기준을 원본 상세 문서 ID로 변경했습니다.
- 같은 원본 문서의 중복 데이터만 묶고, 다른 원본 문서는 자동 병합하지 않도록 처리했습니다.

#### 배운 점
- 표시 내용의 유사성과 데이터의 동일성은 구분해야 한다는 점을 배웠습니다.

### 2. 행사 정보 변경 시 리뷰·즐겨찾기 연결이 분리되는 문제

#### 문제
- 행사 제목, 일정, 참가비 등으로 식별 키를 만들면 해당 값이 수정될 때 새로운 키가 생성됐습니다.
- 기존 행사를 갱신하는 대신 새 DB 행사가 만들어져 기존 리뷰와 즐겨찾기가 이전 ID에 남을 수 있었습니다.

#### 해결
- 식별 기준을 변경 가능한 행사 내용에서 원본 문서 ID로 변경했습니다.
- 기존 DB의 원본 URL로 같은 행사를 찾아 키와 행사 정보를 갱신하되 내부 `festivalId`는 유지했습니다.
- 기존 데이터의 원본 URL이 없거나 중복되는 경우에는 자동 병합하지 않고 확인이 필요하도록 처리했습니다.

#### 배운 점
- 해시 함수를 사용하는 것만으로 식별자가 안정적이 되는 것은 아닙니다.
- 해시 입력값 자체가 데이터의 변경되지 않는 정체성을 나타내야 한다는 점을 배웠습니다.

### 3. 제목 기반 상세 페이지 라우팅이 불안정했던 문제

#### 문제
- 초기에는 행사 제목을 URL path variable로 사용해 상세 페이지에 진입하도록 구현했습니다.
- 하지만 외부 API 데이터에는 `<아이돌; Children Stone>`처럼 특수문자가 포함된 제목이 존재했고, 이 경우 상세 페이지로 정상적으로 접속할 수 없는 문제가 발생했습니다.
- 제목 문자열은 화면 표시 용도로는 적합하지만, URL 식별자나 내부 기능 연결 기준으로 사용하기에는 불안정하다는 점을 확인했습니다.

#### 해결
- 상세 페이지 진입 기준을 제목 기반이 아닌 내부 식별자인 `festivalId` 기반으로 변경했습니다.
- 기존 제목 기반 경로는 호환용으로 유지하며, 정규화된 제목으로 활성 행사를 조회한 뒤 해당 DB ID의 상세 주소로 리다이렉트합니다.
- 행사 목록, 검색 결과, 마이페이지에서 상세 페이지로 이동할 때 모두 `festivalId`를 사용하도록 수정했습니다.

#### 배운 점
- 외부 API의 문자열 데이터는 사용자에게 보여주는 값과 시스템 내부 식별 값으로 분리해서 설계해야 한다는 점을 배웠습니다.
- 특히 URL 라우팅이나 권한/리소스 연결에는 변동 가능성이 있는 문자열보다 안정적인 내부 식별자를 사용하는 것이 유지보수와 확장성 면에서 훨씬 유리하다는 점을 체감했습니다.

### 4. 비밀번호 변경 후 보안 처리

#### 문제
- 비밀번호만 변경하고 기존 세션을 그대로 유지하면, 보안상 애매한 사용자 경험이 될 수 있다고 판단했습니다.

#### 해결
- 비밀번호 변경 성공 시 현재 세션을 종료하고, 다시 로그인하도록 처리했습니다.

#### 배운 점
- 단순 기능 구현을 넘어서, 실제 서비스 관점에서 인증 흐름을 설계해야 한다는 점을 느꼈습니다.

### 5. 애니메이션을 주는 스크립트가 동작하지 않는 것처럼 보였던 문제

#### 문제
- 페이지 전환 효과와 행사 카드 등장 애니메이션이 적용되지 않아 스크립트가 정상적으로 실행되지 않는 것처럼 보였습니다.
- 스크립트 문장을 새로 작성해보거나 애니메이션 수치와 시간을 크게 조정해도 화면상 변화가 없어, 처음에는 JavaScript 코드 자체의 문제의 문제라고 판단했습니다.

#### 원인
- 원인을 추적하는 과정에서 코드 문제가 아니라, 운영체제 Windows의 모션 줄이기 설정이 활성화되어 있는 것이 원인이었습니다.
- 이 설정으로 인해 애니메이션 관련 효과가 제한되거나 비활성화되면서, 스크립트가 동작하지 않는 것처럼 보였습니다.

#### 해결
- Windows의 접근성 설정까지 함께 점검하면서 문제 원인을 다시 확인하였습니다.
- 이후 애니메이션 관련 문제를 디버깅 할 때는 코드뿐 아니라 **브라우저 환경, 운영체제 설정, 접근성옵션** 도 함께 확인하는 방식으로 점검 범위를 넓혔습니다.

#### 배운 점
- 프론트엔드 동작 문제는 항상 코드 자체만의 문제가 아닐 수 있다는 점을 배웠습니다. 
- 특히 애니메이션이나 인터랙션 기능은 사용자 환경 설정의 영향을 받을 수 있기 때문에, 디버깅 시 실행 환경까지 함께 고려하는 습관이 중요하다는 것을 깨달았습니다.

> 아래 내용은 초기 개발 과정에서 겪었던 스키마 변경 경험입니다.
> 현재 동기화에서는 테이블을 삭제하지 않으며, 기존 행사 ID를 유지하는 갱신 방식을 사용합니다.
> `INSERT IGNORE`는 과거 식별자 생성 경로에서 사용했던 방식으로, 현재 동기화 저장은 `FestivalSyncWriter`가 담당합니다.
### 6. 배포 환경에서 기존 DB 데이터와 충돌한 문제

#### 문제
- 로컬에서는 정상적으로 동작했지만, Render 배포 환경에서 카테고리 페이지 접속 시 500 에러가 발생했습니다.
- 로그를 확인해보니 Aiven DB의 기존 `festival` 테이블에 예전 방식의 긴 `identity_key` 데이터가 남아 있었고, 새 코드에서 `identity_key`를 64자리 해시값으로 변경하면서 충돌이 발생했습니다.
- 또한 같은 행사를 거의 동시에 저장하려는 경우 `Duplicate entry` 오류가 발생할 수 있었습니다.

#### 해결
- `identityKey`를 긴 문자열 그대로 저장하지 않고, 행사 정보를 조합한 fingerprint를 SHA-256으로 변환해 저장하도록 수정했습니다.
- `identity_key` 컬럼 길이를 64자로 변경하고, 중복 저장 시 예외가 발생하지 않도록 `INSERT IGNORE`를 적용했습니다.
- Aiven DB에 남아 있던 기존 행사 관련 테이블을 삭제한 뒤, 새 스키마 기준으로 다시 생성했습니다.

#### 배운 점
- 배포 환경에서는 코드 수정만으로 문제가 해결되지 않을 수 있고, 기존 DB에 남아 있는 데이터와 제약조건까지 함께 확인해야 한다는 점을 배웠습니다.

### 7. 외부 API 데이터 제공 중단으로 인해 행사 조회가 불가능해진 문제

#### 문제
- 기존 프로젝트 API는 경기데이터드림의 문화 행사 데이터를 활용해 서비스를 구현했습니다.
- 운영 중 기존 API에서 더이상 행사 데이터가 제공되지 않아 행사 목록이 조회되지 않는 문제가 발생했습니다.
- 서비스 핵심 기능이 외부 API 데이터에 의존하고 있었기에 행사 목록, 검색, 상세 조회 기능이 모두 영향을 받았습니다.

#### 해결
- 대체 가능한 문화 행사 공공API를 조사했습니다.
- 경기문화재단(GGC) API를 신규 데이터 공급원으로 선정하였습니다.
- 기존 XML 응답구조를 JSON 응답 구조로 변경했습니다.
- 기존 DTO 및 응답 모델을 경기문화재단 API 응답 형식에 맞게 수정했습니다.

#### 배운 점
- 외부 API는 언제든지 변경되거나 중단될 수 있으므로 특정 공급원에 과도하게 의존하지 않는 설계가 중요하다는 점을 배웠습니다.
- 비즈니스 로직과 데이터 수집 계층을 분리하면 외부 API가 변경되더라도 서비스 전체를 수정하지 않고 대응할 수 있다는 점을 경험했습니다.
- 실제 운영 환경에서는 새로운 기능 개발뿐 아니라 장애 상황을 분석하고 복구하는 능력도 중요하다는 점을 배웠습니다.

### 8. 외부 API 장애에 대비한 데이터 안정성 개선

#### 문제
- 초기 구조에서는 서비스가 API 데이터에 직접 의존하고 있었습니다.
- API 서버 장애 또는 서비스 중단 시 행사 목록 조회가 불가능해질 수 있었습니다.
- 실제 운영 과정에서 기존 공공데이터 API의 데이터 제공이 중단되는 상황을 경험하여 외부 서비스 의존성을 줄일 필요성을 느꼈습니다.

#### 해결
- Spring Scheduler로 API 수집을 주기적으로 실행하도록 구성했습니다.
- 사용자 조회는 내부 DB를 사용하도록 변경해 외부 API 응답에 직접 의존하지 않게 했습니다.
- 전체 페이지 수집 후 DB에 반영하며, 중간 실패 시 부분 결과를 저장하지 않습니다.
- DB 반영까지 성공한 시각을 별도로 기록해 데이터 최신 여부를 확인할 수 있도록 했습니다.

#### 배운점
- 외부 API는 언제든지 장애가 발생할 수 있기에 서비스 데이터와 외부 데이터 공급자를 분리하는 설계가 중요하다는 것을 배웠습니다.
- 단순 API 연동보다 장애 상황을 고려한 데이터 안정성 확보가 중요하다는 점을 경험했습니다.

### 9. 일부 API 데이터만으로 누락 행사를 비활성화할 수 있는 문제

#### 문제
- API 한 페이지만 받은 뒤 응답에 없는 DB 행사를 모두 비활성화하고 있었습니다.
- 다음 페이지에 존재하는 정상 행사도 API에서 사라진 것으로 오인할 수 있었습니다.
- 실제 API 확인에서는 요청한 페이지 크기보다 적은 개수가 반환돼, 응답 개수만으로 마지막 페이지를 판단할 수도 없었습니다.

#### 해결
- 0페이지부터 정상적인 빈 페이지 또는 데이터 없음 응답까지 순차 수집하도록 변경했습니다.
- 응답 코드와 형식을 검증하고 반복 페이지와 최대 페이지 수 초과를 감지하도록 했습니다.
- 전체 수집이 성공한 경우에만 누락 행사 비활성화를 포함한 DB 반영을 수행하도록 변경했습니다.

#### 배운 점
- API 응답 한 건이 정상이라는 사실과 전체 데이터를 정상 수집했다는 사실은 다릅니다.
- 누락 데이터를 삭제하거나 비활성화할 때는 수집 범위와 완료 조건을 먼저 확인해야 한다는 점을 배웠습니다.

## 아쉬운 점

- 고객센터의 **건의사항 전송 기능**은 UI만 구현되어 있고 실제 전송 기능은 아직 미구현 상태입니다.
- 이번 프로젝트는 기능 구현과 배포 흐름을 우선으로 진행했으며, 주요 기능은 회원가입, 로그인, 상세 조회, 리뷰, 즐겨찾기, 마이페이지 중심으로 수동 검증했습니다.
- 검색 기능은 제목 / 기관명 / 주소 기준으로 개선했지만, 아직 날짜 범위, 지역, 카테고리 등 세부 조건 기반 필터링은 부족합니다.
- 현재 `Review`와 `FavoriteEvent`는 `festivalId`, 로그인 아이디인 `username` 값을 중심으로 연결하고 있어 기능 구현에는 문제가 없지만, 추후에는 JPA 연관관계를 더 명확하게 표현하도록 리팩토링하고 싶습니다.

## 실행 방법

현재 프로젝트는 배포 환경에서 바로 확인할 수 있습니다.

- 배포 주소: https://ggnow-portfolio.onrender.com/main

로컬에서 직접 실행하는 경우에는 MariaDB 연결 정보를 환경 변수로 설정해야 합니다.
현재 사용하는 경기문화재단 API는 별도 인증키 없이 호출합니다.
실행에 필요한 주요 환경 변수는 다음과 같습니다.

```properties
API_BASE_URL=https://ggc.ggcf.kr/open/json/playongoing
API_PAGE_INDEX=1
API_PAGE_SIZE=200

DB_URL=jdbc:mariadb://localhost:3306/ggnow
DB_USER=your_db_user
DB_PASSWORD=your_db_password

PORT=8080
```

**DB_URL**은 실행 방식에 따라 다르게 설정합니다.
- 로컬에 설치된 MariaDB를 사용하는 경우 
```properties
DB_URL=jdbc:mariadb://localhost:3306/ggnow
```
- Docker Compose로 실행한 MariaDB를 사용하는 경우
```properties
DB_URL=jdbc:mariadb://localhost:3307/ggnow
```

## 회고

이번 프로젝트를 통해 단순한 화면 구현을 넘어서, **회원 인증**, **데이터베이스 연동**, **외부 API 처리**, **권한 검증**, **배포**까지 웹 서비스의 전체 흐름을 경험할 수 있었습니다.

특히 백엔드 개발자로서 아래와 같은 부분을 직접 고민하고 구현해본 경험이 의미 있었습니다.

- 외부 API 데이터를 어떻게 정제하고 사용할지
- 화면 표시용 데이터와 내부 식별자를 어떻게 분리할지
- API 장애에 어떻게 대응할지
- 리뷰와 즐겨찾기 같은 사용자 데이터를 어떤 기준으로 연결할지
- 실제 배포 환경에서 설정과 DB를 어떻게 관리할지

처음에는 행사 제목을 정규화해 식별 기준으로 사용했고, 이후 날짜·시간·주소·참가비를 조합한 fingerprint 방식으로 개선했습니다. 하지만 변경 가능한 정보를 식별 키에 포함하면 같은 행사의 내용 수정도 새로운 행사로 인식할 수 있다는 한계를 확인했습니다. 이를 해결하기 위해 원본 상세 문서 ID 기반 식별 방식으로 변경하고, 기존 DB 행사의 내부 ID를 유지하면서 갱신하도록 구성했습니다. 이 과정에서 식별자 설계와 데이터 변경 감지는 서로 다른 문제이며, 기존 사용자 데이터와의 연결을 보존하는 이전 과정까지 고려해야 한다는 점을 배웠습니다.

이 과정을 통해 외부 데이터를 그대로 신뢰하기보다 서비스 목적에 맞게 정제하고, 사용자 데이터와 연결되는 부분은 내부 식별자를 기준으로 설계해야 한다는 점을 배웠습니다.

이번 프로젝트를 진행하면서 API를 연동하는 것보다 서비스가 외부 시스템 장애에 어떻게 대응을 해야 할지 고려하는 것이 중요하다는 것을 배웠습니다.

초기에는 행사 데이터를 실시간으로 조회하는 구조였지만, 실제 데이터 제공 중단을 경험하면서 Scheduler 기반 데이터 수집, DB적재, DB조회 구조로 개선했습니다.

이를 통해 단순 기능 구현을 넘어 데이터 안정성, 서비스 지속성, 운영 관점의 설계까지 고민해볼 수 있었고 백엔드 개발자가 단순히 데이터를 가져오는 역할이 아니라 안정성을 제공하는 역할을 수행해야 한 다는 것을 경험했습니다.

앞으로는 테스트 코드, 예외 처리, 검색 고도화, 운영 환경 설정 분리 등을 보완해 더 안정적인 백엔드 서비스를 개발할 수 있도록 발전시키고 싶습니다.
